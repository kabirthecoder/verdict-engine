verdict-engine · architecture · v0.1 · Sept 2026

A court, not a supervisor.

Multi-agent systems usually put one agent in charge and the rest follow. verdict-engine has no one in charge. Agents write claims, evidence and attacks into one shared graph, and the answer is computed from that graph by a rule that has been proven since 1995. The graph is the proof.

1. The argument graph

Everything any agent or human does ends up as one of seven record types. The graph is append-only: there is no update or delete anywhere in the code. A retraction is a new attack; a correction is a new claim.

Invariants the graph enforces

  1. No support, no standing. An unsupported claim can neither be accepted nor attack anything.
  2. Evidence is written only by the runtime and never edited; its hash is part of the record.
  3. An attack is a claim, so it can be attacked back and needs its own evidence.
  4. Every node carries an author: role + run id for agents, user id for humans.
  5. Nothing is deleted. A failed audit is a new node, not a removed one.

Where it lives

Seven tables in SQLite for a laptop, Postgres for a service; SQLAlchemy Core, JSON columns for the flexible parts. src/verdict/graph. Loading a question returns an immutable Graph snapshot the engine and the roles read from.

2. How the verdict is computed

The graph induces an abstract argumentation framework (Dung, 1995): supported claims are the arguments, attack edges are the attack relation. The engine computes the grounded extension: the unique, most skeptical set of claims that defend themselves against every attacker. It is a fixed-point iteration, pure Python, a few milliseconds for thousands of nodes.

Labelling rules

  1. Drop every claim with no surviving support → unsupported.
  2. A claim whose attackers are all rejected (or that has none) → accepted.
  3. A claim with an accepted attacker → rejected.
  4. Repeat until nothing changes. Whatever is left → undecided.

Why grounded, not "preferred"

Other semantics let the system choose between several self-consistent worlds. Grounded never chooses: two claims that only attack each other stay undecided, and the page shows exactly which attack nobody could settle. For a decision system, saying "I don't know, and here is why" is the feature.

3. The court loop

There is no scheduler deciding who speaks next. Each round, the loop looks at the graph and fires whichever roles have a trigger condition. A round that writes nothing is a fixed point; then the verdict is frozen with the graph. Budgets (rounds, tool calls, wall-clock) are hard stops.

4. Tool calls as evidence

A tool is a typed Python function; the decorator derives its JSON schema from the signature and docstring. The runtime executes it, serializes the result, hashes it, and writes the Evidence node. The agent receives {evidence_id, ok, summary, output} and can only cite what it caused to be produced. Identical calls within a case return the same node, so evidence cannot be inflated by repetition. Failures are evidence too (ok:false) and a citation to one fails audit automatically.

@tool
def osv_query(ecosystem: str, package: str, version: str) -> VulnQuery:

5. Domains are plug-ins

The court, roles, runtime and engine never change per domain. A domain contributes a claim vocabulary (kinds with identifying parameters, so two agents asserting the same thing produce the same key), a tool set, role guidance, and which kinds are conclusions. The first domain is supply-chain trust; incident root-cause, vendor due diligence or clinical evidence would reuse everything but this file.

7. What "production" means here

Reproducible. Same graph, same verdict, always. A case can be reopened months later with new evidence; the old verdict stays in history.

Auditable. Every accepted claim traces to a tool, its arguments, a hash of its raw output, and a quote the auditor checked against that output.

Bounded. Rounds, tool calls, episode steps and wall-clock each have hard limits; the verdict records why the loop stopped.

Measured. verdict eval runs real historical attacks (event-stream, ua-parser-js, colors, node-ipc, requests CVEs) and scores conclusion accuracy, required claim kinds, and citation faithfulness.
